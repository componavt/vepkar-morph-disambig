# Метазапрос для компактного CLI Prompt

Сформулируй один компактный CLI prompt **на английском языке** для Qwen3-Coder-Next.

Актуальное состояние реального репозитория содержится в приложенном repository snapshot `semcat_NN.md`.

CLI prompt должен охватывать только выбранную подзадачу:

```text
<НАЗВАНИЕ ВЫБРАННОЙ ПОДЗАДАЧИ>
```

В ответе выведи **только готовый CLI prompt на английском языке**. Не добавляй русский вводный текст, анализ, объяснение или иной текст вне prompt.

---

## Назначение и границы

Сформулируй точный, самодостаточный и экономный implementation prompt для реального Python-репозитория семантической категоризации VepKar. В нём есть Python CLI-модули, pandas-преобразования, CSV data contracts, офлайн pytest-тесты и необязательные runtime-компоненты для моделей и лингвистических ресурсов.

Каждый CLI prompt выполняется в новой независимой сессии VS Code / Kilo Code. Поэтому он должен содержать только контекст, необходимый для текущей подзадачи.

Не ссылайся на текущую беседу, repository snapshot, историю, предыдущие или будущие работы. Не предлагай coding agent читать приложенные файлы: он должен читать только реальные файлы репозитория, нужные для текущей задачи.

Не расширяй scope на соседние работы. Проблему вне scope не исправляй попутно; кратко укажи её в `Known limitations` лишь если она мешает выполнению выбранной задачи.

---

## Пути и изменения

В CLI prompt требуй:

- использовать реальные текущие пути, API, поля и тесты, проверенные в репозитории;
- указывать файлы полными относительными путями от корня;
- сначала перечислять точные in-scope файлы;
- не менять несвязанные модули, зависимости, lock-файлы, конфигурацию, README и настройки тестов;
- объяснять в final report необходимое изменение вне первоначального scope;
- удалять dead code, compatibility code и обслуживающие их тесты только тогда, когда выбранная задача устраняет их последний production-потребитель.

Не придумывай пути, поля, API или тесты. Не переименовывай файлы и модули ради стиля.

---

## Data contracts и семантика

Считай CSV schemas и значения DataFrame публичными data contracts.

Если задача затрагивает CSV или DataFrame, включай только применимые требования:

- входные и выходные файлы;
- условия создания output;
- правила включения и исключения строк;
- изменяемую schema, обязательные поля и их порядок;
- правила для null, empty и производных значений;
- составной ключ, уникальность и join cardinality, если они существенны;
- поля, намеренно отсутствующие в публичном output.

Не допускай, чтобы writer или helper молча исправлял отсутствующие поля или фабриковал бизнес-значения. Производные данные и групповые статистики должны вычисляться там, где доступны необходимые исходные данные.

Если задача меняет взаимоисключающую классификацию, потребуй проверяемый conservation invariant, подходящий именно для этой классификации.

Если это релевантно выбранной задаче, сохраняй утверждённое направление проекта:

- единица перевода и семантической обработки — полное словарное значение;
- используются поля `pos`, `meaning_ru`, `meaning_en` и, для round-trip QA, `meaning_ru_back`;
- идентичность задаётся парой `("pos", "meaning_ru")`;
- не вводи сериализованный дублирующий идентификатор, если эта пара уже присутствует;
- дедупликация и merge используют составной ключ, когда это требуется;
- не возрождай legacy-терминологию коротких глосс без прямой необходимости в scope.

---

## Реализация и тесты

Формулируй короткие, упорядоченные и наблюдаемые требования. Включай кодовый фрагмент только когда без него возможна существенная ошибка в критической логике. Не вставляй большие шаблоны, полные файлы, альтернативные варианты реализации или иллюстративный код, который agent способен вывести из требований.

Не добавляй silent fallback, broad exception swallowing, неявную миграцию несовместимых данных, compatibility alias или автоматическое переименование schema без прямого требования задачи. Не ослабляй assertions, не отключай и не skip-ай существующие тесты, не меняй dependency/runtime configuration вне scope.

Если задача меняет воспроизводимое поведение, CLI, DataFrame transformation, CSV schema, persistence, classification или data semantics, потребуй focused offline tests. Они должны быть быстрыми, детерминированными, работать на synthetic data и `tmp_path`, не требовать реальных экспортов, LLM, сети, Hugging Face downloads, CUDA, NLTK downloads или proxy.

Для исправляемого дефекта потребуй regression test. Для CSV-задач, когда применимо, требуй проверки непустого и пустого output, точной schema, ключевых строк, отсутствующих публичных полей, уникальности и join cardinality.

Требуй запуск всего релевантного focused test file или directory, а не отдельных новых тестов. Если нерелевантный тест падает из-за optional dependency, agent должен назвать команду, тест и краткую причину, не скрывая failure.

Добавляй одну безопасную manual validation command только когда она даёт дополнительную ценность и не запускает LLM, не требует сети и не перезаписывает обычные artifacts.

---

## Экономия вывода

CLI prompt должен прямо требовать от coding agent режим **quiet execution**:

- Выполняй работу молча: не публикуй план, рассуждения, промежуточные итоги, status updates, перечни прочитанных файлов, tool-call narration, diff, содержимое файлов или полный test output.
- Не объясняй очевидные мелкие изменения: imports, отдельные строки, локальные переименования и механические правки.
- Не повторяй требования задачи в ходе работы или в final report.
- Не печатай успешные результаты команд; сохрани только их итоговые counts и существенные ошибки для final report.
- Если возникла блокирующая неоднозначность, задай один короткий точный вопрос. Во всех остальных случаях прими решение по текущему коду и требованиям задачи.
- Отчёт о выполнении выдай один раз, только после всех изменений и проверок.

Сгенерированный CLI prompt должен быть достаточно подробным для корректной реализации, но без повторов, длинных объяснений, исторического контекста и необязательных примеров.

## Структура CLI prompt

Сформируй только применимые разделы:

1. `TOOL-CALL DISCIPLINE`
2. `TASK`
3. `SCOPE`
4. `CURRENT PROBLEM`
5. `REQUIRED IMPLEMENTATION`
6. `TESTS`
7. `OBSERVABLE COMPLETION CRITERIA`
8. `VALIDATION COMMANDS`
9. `FINAL REPORT`

В `TOOL-CALL DISCIPLINE` потребуй использовать доступный native structured editor/tool interface, читать точный фрагмент до редактирования и делать небольшие атомарные изменения. Agent должен следовать реальной schema доступного инструмента и не печатать псевдо-tool calls.

---

## Ограничение final report

Потребуй один итоговый отчёт **не более 450 токенов**. Он должен иметь ровно четыре кратких подраздела:

1. `Changed files`
   - Только реально изменённые полные относительные пути.
   - Одно короткое пояснение лишь для изменения вне scope.

2. `Implemented requirements`
   - От 2 до 6 коротких пунктов только о наблюдаемом поведении, schema/API и удалённом dead code.

3. `Tests run`
   - Только точные команды и итог `passed/failed/skipped`.
   - Без полного pytest output, traceback и командного журнала.

4. `Known limitations`
   - Один пункт `None`, если существенных ограничений нет.
   - Иначе только незавершённость, failure, отклонение от scope или блокирующая зависимость.
   - Для failure: команда или тест плюс одна короткая root cause.

Не называй задачу завершённой, если релевантные tests не прошли. Не пересказывай prompt, ход работы, tool calls или полные изменённые фрагменты кода.
