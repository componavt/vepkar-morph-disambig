# vepkar-morph-disambig

В этом репозитории исследуется ранжирование кандидатных морфологических
разборов слов в контексте корпуса VepKar: если для словоформы получено одно
или несколько возможных разборов, задача — ранжировать их с опорой на
корпусные данные.

Репозиторий будет содержать реализации владельца всех трёх направлений
исследования:

- `src/core/` — код, общий для трёх направлений.
- `src/t1_features/` — ранжирование морфологических кандидатов на основе
  признаков.
- `src/t2_context/` — методы, использующие контекст.
- `src/t3_transfer/` — эксперименты по переносу (transfer).

## Статус

Каркас CLI, загрузка исходных данных по Git tag, типизированное чтение корпуса
с проверкой схемы и связей (`inspect-data`), построение воспроизводимых
морфологических обучающих задач (`build-instances`) и детерминированное
разбиение целых текстов на `train/dev/test` (`make-splits`) реализованы. Модели
и оценка ещё не реализованы.

## Использование

Нужны Git и Python версии 3.11 или новее. Один раз загрузите все исходные
выгрузки, указав опубликованный tag репозитория `componavt/dictorpus-data`:

```bash
python3 src/cli.py fetch-data v2026.09
```

В 2026 году `v2026.09` является опубликованным и рекомендуемым tag для
первого локального получения данных. Команда создаст `data/dictorpus-data/` —
локальный клон, исключённый из Git этого проекта. Повторный вызов с тем же tag
не меняет чистый клон; клон другой версии или с локальными изменениями не
заменяется. Будущие эксперименты будут читать данные локально без повторного
указания tag.

```bash
python3 src/cli.py --help
python3 src/cli.py --version
python3 src/cli.py inspect-data krl
python3 src/cli.py build-instances
python3 src/cli.py make-splits
```

`inspect-data` читает локальную выгрузку корпуса из
`data/dictorpus-data/corpus/`, превращает четыре таблицы корпуса в типизированные
DataFrame и выводит число строк, проверку схемы и идентификаторов, целостность
связей и дубликатов, распределения кандидатов по словам и диагностику
экспертных пометок `relevance=2`. Поля `corpus_id` и `genre_id` с разделителем
`|` разбираются в кортежи `corpus_ids` и `genre_ids`. Команда выводит все
доступные диагностики до того, как вернуть ненулевой код выхода при нарушенных
связях или дубликатах ключей. Нулевые значения `word_number` и пустые значения
`gramset` сохраняются и сообщаются как находки, а не удаляются. Для каждого
сообщённого класса находки выводятся не более трёх контекстных примеров с
исходным `sentence_xml`, когда связь однозначна; если `sentence_xml` получить
нельзя, причина указывается явно. Файл с построчными проблемами не создаётся.
Команда не создаёт производных данных и не изменяет `dictorpus-data`.
Необязательный флаг `--data-dir` задаёт другое расположение выгрузки
(используется в автономных тестах). `inspect-data` остаётся отдельной детальной
командой диагностики исходных данных и не применяет воронку отбора бенчмарка.

`build-instances` читает каждую из четырёх языковых разновидностей по очереди
из той же локальной выгрузки, строит одну задачу ранжирования на одно
вхождение слова в корпусе и печатает одну компактную сводную таблицу (с одной
короткой строкой прогресса по каждой разновидности в stderr):

```text
0. все исходные слова
1. слова с >=2 строками кандидатов и ровно одной строкой relevance=2
2. ... с >=2 различными анализами (wordform_id, gramset)
3. ... без повторяющейся идентичности кандидата
4. ... у которых выбранный анализ имеет непустой gramset
5. ... чьё предложение связано с одним однозначным существующим текстом
6. ... чьё предложение целиком имеет только уникальные положительные word_number
7. ... у которых каждый кандидат имеет непустой gramset
```

Вхождение слова с любым кандидатом, имеющим пустой `gramset`, исключается из
основного бенчмарка целиком (шаг 7); пустой `gramset` у невыбранного кандидата,
прошедшего шаг 4, учитывается как потеря шага 7 и не пересчитывается повторно.
Исходные файлы `candidate_analyses_*.csv.zst` и `inspect-data` по-прежнему
сохраняют и сообщают пустые `gramset`. Для tag `v2026.09` измеренная отсылка —
около 28 400 задач после шага 6 и новый основной пул около 28 017; команда
печатает фактически вычисленные числа. Команда также записывает единственный
файл для проверки разработчиком
`data/derived/quality/zero_word_number_sentences_<tag>.csv` со схемой ровно
`language,sentence_id`, по одной строке на каждое предложение, содержащее
`word_number == 0`, отсортированный детерминированно и построенный из всех
строк `words`. Tag в имени файла определяется из локальной Git-выгрузки;
исходные данные не изменяются. Необязательные флаги `--data-dir` и
`--output-dir` задают другое расположение выгрузки и производных файлов
(используется в автономных тестах).

`make-splits` строит те же первичные задачи шага 7 без повторного отчёта
`build-instances` и относит каждый целый текст каждой языковой разновидности
ровно к одному из `train` / `dev` / `test`. Назначение минимизирует отклонение
от целевой доли кандидатных строк: 80% train, 10% dev и 10% test на каждую
разновидность, с документированным фиксированным зерном (`20260928`), фиксированным
числом перезапусков и детерминированным разрешением связей; 80/10/10 — это цель,
а не точная гарантия. Создаётся единый общий CSV `data/derived/splits_<tag>.csv`
со схемой ровно `language,text_id,split`, уникальный и отсортированный
детерминированно по языку и числовому `text_id`. Если этот файл уже существует
с идентичным содержимым, он не трогается; если отличается, команда завершается
с ошибкой, а не перезаписывает общее тестовое разбиение. После успешной
обработки всех четырёх разновидностей команда печатает две компактные таблицы
(состав бенчмарка и распределение разбиения с фактическими процентами
кандидатов). И `build-instances`, и `make-splits` выводят прогресс максимум
четырьмя flushed-строками stderr на команду.


## Данные

Корпусные данные поступают отдельно из `dictorpus-data` и в этот репозиторий
не коммитятся. Общие производные входные данные будут лежать в `data/derived/`.
